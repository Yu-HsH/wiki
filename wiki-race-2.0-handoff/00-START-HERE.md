# Wiki Race 2.0 새 채팅 인수인계 안내

작성 기준일: 2026-08-13  
상태: 게임 규칙 확정, 구현·디자인 분리 진행

## 1. 이 묶음의 목적

Wiki Race 2.0 작업을 한 채팅에 모두 넣지 않고 다음 세 흐름으로 분리한다.

1. 기능별 코드 검토 채팅: 저장소를 읽고 현재 구현과 확정 규칙의 차이를 찾는다.
2. 기능별 Codex 구현 채팅: 승인된 계획만 실제 코드로 구현하고 테스트한다.
3. 디자인 채팅: 코드와 분리해 화면 구조·상태·PC/모바일 시안을 먼저 확정한다.

`01-CONFIRMED-SPEC.md`가 모든 채팅의 단일 기준 문서다. 기능 파일과 충돌하면 공통 명세를 우선하고, 공통 명세에 없는 사항은 임의로 확장하지 않는다.

## 3. 권장 채팅 순서

### 채팅 A — 저장소 전체 감사

첨부:

- `01-CONFIRMED-SPEC.md`
- `code/10-CODE-MASTER-TODO.md`
- `code/11-REPOSITORY-AUDIT.md`

목표:

- 현재 브랜치·커밋·변경사항 확인
- 완료·부분 구현·미구현·규칙 불일치 분류
- 기능별 실제 수정 파일과 의존성 확인
- 이후 기능 채팅 순서 확정

이 채팅에서는 대규모 구현을 시작하지 않는다.

### 채팅 B~G — 기능별 코드 작업

각 채팅에는 다음만 첨부한다.

- `01-CONFIRMED-SPEC.md`
- 해당 기능 파일 한 개
- 저장소 감사 결과 중 해당 기능 부분

한 채팅에서 여러 기능을 동시에 구현하지 않는다. 공통 스키마 변경이 다른 기능에 영향을 주면 먼저 영향 범위를 보고하고, 승인된 범위만 수정한다.

## 4. 작업 상태 표기

- `[ ]`: 시작 전
- `[~]`: 분석 또는 구현 중
- `[x]`: 자동 테스트와 수동 검증까지 완료
- `[!]`: 차단됨. 원인·필요 결정·재현 방법 기록
- `[D]`: 2.0 이후로 명시적으로 보류

코드를 작성했다는 이유만으로 `[x]`로 바꾸지 않는다. 관련 테스트, 빌드, 핵심 수동 흐름까지 통과해야 한다.

## 5. 모든 새 채팅의 공통 규칙

- 마지막으로 알려진 브랜치는 `fix/wiki-link-stability`지만 매번 실제 브랜치를 확인한다.
- 사용자 변경과 더러운 작업 트리를 임의로 되돌리지 않는다.
- 그룹 DB/RPC/RLS 안정화는 이미 완료된 영역이므로 근거 없이 재작성하지 않는다.
- 그룹 안정화 기준 커밋으로 `37adc698c40356ec61af0faf0aff84eb6fadf90b`가 보고됐으나, 원격 반영 여부와 현재 포함 여부를 먼저 확인한다.
- Wikipedia 본문 읽기와 링크 선택이 화면의 최우선이다.
- 그룹에는 아이템을 넣지 않는다.
- 구현된 기존 기능을 명시적 근거 없이 삭제하지 않는다.
- 새 규칙은 가능한 한 설정·카탈로그 데이터로 분리해 추후 확장 가능하게 한다.
- 서버가 승패·이동·아이템 소비·XP·업적을 최종 확정한다.
- PC와 모바일, 키보드, 터치, 모션 감소 상태를 함께 검증한다.
