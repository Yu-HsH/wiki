# 공개방 / 비공개방 기능 계약 (v2.0.x 초안)

## 목적과 범위
- 모드: 1:1(2명), 그룹(3~8명).
- 방 생성 시 `공개` 또는 `비공개` 선택. **기본값은 비공개**로 기존 동작을 보존한다.
- 비공개: 기존 방 코드 참가 유지. 공개 목록에는 표시하지 않는다.
- 공개: 방 목록에 나타나며 코드 없이 목록에서 참가할 수 있다. 코드 참가도 허용한다.
- 비로그인·게스트는 공개방 목록 및 멀티플레이 참가 불가.
- 상태 `waiting`이며 유효 인원 < 정원인 방만 참가 가능. 방 조회 후 입장 경쟁은 서버에서 원자적으로 재검사한다.

## 모델 변경 제안
- `public.game_rooms.is_public boolean not null default false`
- 기존 방은 모두 비공개로 마이그레이션한다.
- 목록은 공개 대기방의 최소 필드만 조회한다: room ID, 모드, 정원, 인원, 방장 표시 이름, 1:1 아이템 여부, 생성 시각.
- 목록 전용 `list_public_waiting_rooms_v1(mode)` RPC 사용. 본래 `game_rooms` 행 전체를 공개 반환하지 않는다.
- 공개방 참가는 `join_public_room_v1(room_id)` RPC에서 검증 후 기존 모드별 join 계약으로 연결한다. 보안상의 이유로 기존 참가 RPC의 서버 권한·상태·정원 검증을 재사용한다.

## 보안 필수 결정
1. 현재 `game_rooms` SELECT RLS는 **모든 waiting 방**을 로그인 사용자에게 노출한다. 목록만 숨겨서는 비공개 보안이 충족되지 않는다. 별도 SELECT 정책 정리/검증이 필요하다.
2. 비공개 코드 조회를 정책 변경 후에도 유지해야 한다. `findRoomByCode` / `findGroupRoomByCode`의 직접 `select('*')`는 제한된 `find_room_by_code_v1(code,mode)` RPC로 대체한다.
3. 기존 1:1, 그룹 로그인/참가, 재입장, 방장 변경, 새로고침, 경기 시작을 깨지 않는 권한 회귀 테스트가 필요하다.
4. 공개 목록에는 방 코드, 비공개 방 ID, 문서 진행 정보, 플레이어 경로, 인증 정보 등을 반환하지 않는다.
5. SQL 적용은 운영 DB가 아닌 별도 개발/검증 환경에서 수행 후 승인한다.

## UI
- 1:1 또는 그룹 선택 → 방 만들기: 공개/비공개 토글, 기존 옵션 유지.
- 방 참가: 코드 입력 유지 + 공개방 목록(방장, 현재/정원, 옵션, 새로고침).
- 공개방이 없을 경우 빈 상태. 대기 중에 방이 종료되거나 꽉 찼을 경우 서버 에러를 안내하고 목록을 재조회.
- 목록 실시간 업데이트는 선택적이며, 1차는 명시적 갱신/짧은 폴링으로 시작 가능.
