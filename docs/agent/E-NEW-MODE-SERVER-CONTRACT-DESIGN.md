## 구현 전 선택할 계약

- **이모티콘은 단계별 전송 권위가 우선입니다.** 공개 토픽이나 클라이언트가 주장하는 방·발신자 값으로 접근을 허용하지 않습니다. v4는 전용 명령과 짧은 수명 수신자 투영을 우선 비교하고, S5는 이미 쓰는 수신자 투영과 호환을 먼저 검토합니다. 사용자별 읽기와 발신 권한을 방의 기존 자격으로 제한합니다.
- **관전은 기존 문서 읽기 권한 확장이 필요합니다.** 현재 본인 문서 RPC의 제한을 넓히기보다 관전용 읽기 계약을 별도로 두는 것이 검토 출발점입니다. 응답은 고정 리비전·현재 방에 묶고, 대상 교체·보호 정보·관전 종료의 정책을 승인의 일부로 확정합니다.
- **아이템 피드백은 서버 결과를 원자적으로 기록합니다.** 성공을 확정하는 기존 트랜잭션에서 피드백 식별자와 수신자를 함께 기록할지 검토합니다. 새 이벤트는 원본 사건 ID와 수신자를 기준으로 중복을 막습니다. 실시간 신호와 만료 전 재조회는 같은 이벤트를 읽고, 화면은 한 번만 재생합니다. 발신·피해·설치 역할에 이미 공개되는 데이터만 전달하며 기존 인벤토리, 타이머, 예약, 정산, 입장 계약은 유지합니다.
- **공통 저장소는 선택 사항입니다.** E1·E2의 짧은 반응과 E4·E5의 확정 영수증에 동일한 보존 기간을 강제할 이유가 있는지 먼저 확인합니다. 별도 저장 구조가 필요할 때 새 migration에서 최소 역할·권한, 수신자 한정 읽기, 정리 책임, 기존 앱과의 호환을 명시합니다. Schema 변경 없이 기존 승인 계약을 재사용할 수 있는 부분은 변경량이 더 작은 선택으로 남깁니다.

## 출시 의존성과 좁은 검증

1. E1·E2는 각각 기존 방 인증을 확정한 뒤 검토합니다. E3는 읽기 정책을 별도로 승인할 수 있습니다. E4·E5는 동일한 수신자 피드백 설계를 공유하되 서로 독립적으로 검증합니다.
2. 승인 시 새 migration은 기준 64개 뒤에 별도 추가하고, 기존 앱은 새 응답이 없어도 계속 동작하도록 계약을 정합니다. A·D 브랜치에는 E용 버튼·호출·활성화 조건을 추가하지 않습니다.
3. 변경된 계약만 격리 테스트합니다. 두 실제 계정과 비참가자 한 명의 단계·수신자 확인, 원자적 이벤트 기록·재시도·플레이 재개·종료 확인, 관련 사용자 화면의 1회 표시를 기본으로 둡니다. 기존 전체 감사와 DB 리허설은 재사용합니다.
