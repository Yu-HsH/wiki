- Edge: 신규 `duel-search` **1개**, parse5 7.3.0 포함. `verify_jwt=false`와 `getUser` 인증을 함께 적용한다. 기존 `wiki-snapshot` 등 Edge 재배포는 필요 없다.
- 프론트: 승인된 통합 SHA의 main 병합에 따른 자동 Production 배포 **1회**. 별도 CLI Production 배포를 겹쳐 실행하지 않는다.
- 선행 차단: 실제 약5.7MB 문서 cache miss가 CPU 제한으로 반복 실패한다. [성능 기록](SEARCH-PERFORMANCE-2026-11-02.md)의 문제를 해결하고 같은15초로 다시 검증하기 전에는 다음 운영 단계로 가지 않는다.

## 3. 구형 클라이언트와 쓰기 제한

현재 `utils/maintenanceGate.js`의 `VITE_MAINTENANCE`는 빌드 시 값이다. 점검 배포를 해도 이미 열린 구형 탭·직접 RPC 호출을 서버에서 막지 못한다. 이 값을 켜는 것만으로 안전한 cutover라고 판정하지 않는다.

현재 검색 migration은 활성화 때 session을 추가하지만 구형 탭의 DOM 검색을 호출하도록 강제하지 못한다. 새 Edge만 배포해도 구형 탭은 기존 로컬 검색을 계속한다. 따라서 **새 경기 진입 차단 → 기존 1:1 경기 drain → 서버에서 구버전 신규 시작 거부 → 새 프론트 확인 → 재개**가 필요하다.

코드에서 확인한 진입 경로는 `create_discoverable_duel_room_v1`, `join_duel_room_v2`, `join_public_room_v1`, `start_duel_room_v2`, `initialize_duel_player_v2`다. 이 목록만 revoke하면 충분하다고 단정하지 않는다. 운영의 모든 legacy/wrapper/Edge 호출 경로와 기존 EXECUTE ACL을 읽어 검토한 후, 필요한 **서버 진입 제한 변경안 자체를 별도 승인**받아야 한다. 이번 후보에 임의의 운영 게이트 migration은 추가하지 않았다.

제안하는 제한 범위는 신규 1:1 생성·입장·시작이다. 기존 경기의 heartbeat·이동·기권·최종 결과 확정·XP 처리는 유지해 drain이 가능해야 한다. 진행 경기0 및 활성 검색 세션0 확인 후 DB/Edge를 바꾼다. 안전한 진입 제한이 마련되지 않거나 중단 창을 승인받지 못하면 **HOLD**한다. 싱글·그룹까지 중단할지는 적용 창 승인에서 명시하며, 일괄 쓰기 차단으로 XP 정산을 끊지 않는다.

## 5. 검색만 비활성화할 수 있는가

**현재 즉시 사용할 수 있는 검증된 서버 kill switch는 없다.** 카탈로그에 서버 운영용 enabled 설정이 존재한다고 추측하지 않는다. 프론트 버튼 숨김, Edge만 중단, Vercel 환경변수 변경은 구형 DOM 검색을 막지 못한다. Edge만 중단하면 새 클라이언트는 실패 안전이지만 이미 소모한 슬롯과15초 기회는 복원되지 않는다.

검색만 안전하게 닫는 대안은 서버의 `use_duel_item_v3`에서 `search_once` 신규 활성화를 거부하고, 지급·기존 활성 세션·새 prepare/commit 정책을 함께 검토하는 별도 forward 변경이다. 기존 경기 종료와 활성 세션 drain 후 적용해야 구형 탭까지 같은 경계로 제한할 수 있다. API 실패 코드·UI 안내·다른 아이템 및 쿨타임 영향·동시 요청을 먼저 로컬 검증해야 한다. **이번에 이를 구현하거나 운영에 적용하지 않았다.** 필요 시 구체 변경안과 건별 승인을 먼저 확보한다.

## 6. Rollback 원칙

최근 정상 Production 참고 대상은 `4MdbEvoe5bArd9Fd1BvyTc8xpGgv` / main `8da7d25`다. 이 값은 적용 직전에 Vercel alias/Ready/SHA를 다시 조회해야 하며 예전 legacy RPC 삭제 이전 프론트로는 돌아가지 않는다.

- DB 적용 전: feature 후보를 보존하고 중단한다. 운영 변화가 없다.
- DB만 적용 후: additive 테이블/RPC는 남긴다. 진입 제한을 유지하고 Edge·프론트를 완료하거나 승인된 검색 비활성화 경로를 사용한다. 구형 프론트 정상 실행을 보안 해결로 간주하지 않는다.
- Edge까지 적용 후: 새 프론트 실패라면 새 backend를 남긴 채 제한을 유지한다. 기존 정상 프론트 alias 복구는 **기존 검색 우회도 복원**하므로 보안 승인 없는 정상화로 쓰지 않는다.
- 새 프론트 후: 가장 안전한 복구는 서버 권위를 유지하는 직전 검증 프론트다. 이번 첫 전환에는 그런 운영 대상이 아직 없다. 없으면 검색 제한/점검을 유지하고 수정 후보를 재검증한다. 가용성을 위해 기존8da로 돌아가야 한다면 검색 위험과 제한 방식을 명시해 별도 승인받는다.
- 운영 QA 실패에 대해 경기·XP를 직접 수정하거나 역방향 migration을 임의 실행하지 않는다. 정산 복구는 별도 계약과 승인으로 처리한다.
