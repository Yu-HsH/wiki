## 3. 실제 운영 RPC·권한·정산 계약

실제 운영 함수 원문·EXECUTE·트리거를 조회했으며 격리 복원본 정의와 대조했다 [산출물]. 공개 RPC는 SECURITY DEFINER / 빈 search_path, anon 실행 불가, authenticated/service_role 실행 가능이다. 사용자 호출은 실제 참가자 검증을 거친다. private XP 보조 함수의 authenticated/service_role 직접 실행은 불가다. game_rooms/room_players/match_history/xp_ledger의 일반 회원 직접 INSERT/UPDATE/DELETE는 revoke되어 있고 RLS가 켜져 있다.

|---|---|
| `finalize_duel_if_expired(uuid)` | `1553b9ccf7e0e6a7edeb200a5cf32f97`; 방 FOR UPDATE, finished 재호출 동일, playing 및 참가자 정확히 2명 필요 |
| `leave_duel_room_v2(uuid,uuid)` | `e01f36d73f630399c83c0a83ef0f9a3c`; auth.uid 및 실제 참가자 필요, 요청 ID 재시도 보존 |

만료 기준은 36건 모두 reconnect_deadline_seconds=60이며 heartbeat NULL 또는 now−60초보다 과거다. 양쪽 만료이면 기존 RPC가 2명을 retired/disconnected_timeout으로, 방을 finished/cancelled로 전환하고 cancelled/disconnect_cancelled 결과를 1행 남긴다. XP·업적 트리거는 cancelled 결과를 제외하므로 이 조건에서 XP 원장 신규 0행이다. 이것은 정상 RPC의 결과이며 운영자가 winner/result/XP 값을 직접 지정하는 절차가 아니다.

33개 구형 방은 game_starts_at도 NULL이다. 기존 RPC의 duration 계산식에서는 NULL인 경우 0이 되고, 최근 3개 방은 실제 시작부터 호출까지의 긴 경과 시간이 기록된다. 격리 리허설에서도 이 차이를 그대로 관측했다. 시간을 임의 축소하거나 과거 종료 시각을 만들어 넣지 않는다.

한쪽만 만료되고 다른 쪽이 살아 있으면 같은 RPC는 정상 disconnect_forfeit를 판정한다. 기본 승자 30 XP/패자 0에 동일 상대 감쇠가 적용될 수 있다. 양쪽 모두 살아 있으면 no-op다. 이 함수에는 expected version 조건이 없으므로 사전 조회와 호출 사이 재접속 경쟁을 완전히 제거하지 못한다. 새 활동을 발견하면 즉시 중단·재분류한다. 미래 실행에서도 무조건 0 XP라고 약속하지 않으며 정상 서버가 이미 확정한 결과를 수동 취소/보정하지 않는다. “취소만 허용, 그 외에는 원자적 중단”이 별도 요구라면 조건부 관리 RPC를 추가 승인·검증해야 한다.

서비스 역할을 가진 정상 서버 실행자는 만료 RPC를 호출할 수 있으나, 기권 RPC는 service_role만으로도 `AUTH_REQUIRED`다. 운영에서 사용자 JWT를 흉내 내거나 auth.uid를 주입해 기권시키지 않는다. waiting에서 leave는 참가자/빈 방을 삭제할 수 있으므로 이번 미종료 drain의 관리 도구로 사용하지 않는다.

이번에는 제품 코드 수정이 없어 npm/build를 다시 실행하지 않았다. 기존 npm765/765·build 및 실제 UI/게임 회귀 수치는 [CPU/릴리스 보고서](SEARCH-CPU-2026-11-03.md)의 당시 기준/산출물로 구분한다. 실제 Production 로그인·게임·XP QA 통과로 재사용하지 않는다.

## 5. 별도 판단이 필요한 4건

| 사례 | 기존 경로를 사용한 로컬 모의 결과 | 안전한 다음 선택 |
|---|---|---|
| D01, D02 | initialize 오류. 실제 host가 스스로 leave하면 forfeit, 상대 승자, 각 독립 모의에서 신규 XP 2행/합계 +30 | 실제 본인이 자발적으로 결과 영향을 알고 기권하거나, 별도 무승자·무XP 복구 정책 승인 |
| D28, D32 | initialize 오류. 실제 host가 스스로 leave하면 winner NULL인 forfeit, 각 신규 0 XP 원장 1행 | 실제 host의 자발적 정상 호출 또는 비정상 roster를 위한 별도 복구 정책 승인 |

D01/D02의 +30은 각 케이스를 rollback한 독립 모의다. 실제 연속 정산의 동일 상대 감쇠까지 합산 보장하는 수치가 아니다. 0 XP 원장도 새로운 기록이며 임의로 지우지 않는다. 실제 참가자의 협조 여부는 미확인이고 운영자에게 그 사람을 대신할 권한이 생기는 것은 아니다.

권장 복구 제안은 **네 사례를 정확히 한정한 감사 가능한 서버 복구 RPC**다. 사전 승인된 room/version/roster/활동 지문, 장기 미활동·snapshot 부재·기존 결과/XP 없음, 게이트 닫힘을 잠금 안에서 다시 검사하고 조건 변화 시 전체 중단한다. 허용할 결과는 무승자 cancelled, XP·업적 지급 없음, 보존 가능한 종료 원인과 요청 ID/승인 근거 감사 기록이다. 구현 시 기존 CHECK/트리거/참조 계약과 재시도·동시 heartbeat를 검증해야 한다. 이는 **현재 서버 기능도, 승인된 원래 4개 migration도 아니다**. 직접 status UPDATE/DELETE, 임의 winner/XP, 참가자 추가, 가짜 초기화로 우회하지 않는다. 복구 정책/구현/원문을 별도로 승인하기 전에는 4건을 남겨 두고 HOLD한다.

## 6. QA 2계정만 입장하는 방법

현재 후보의 entry_open은 전역 boolean이고 계정 예외가 없다. entry_open=false이면 QA도 거절된다. required_protocol은 호환성 표식이며 신원이 아니므로 “비밀 protocol을 아는 QA만 허용”하거나 entry_open=true로 열 수 없다. 기존 4개만으로는 사용자의 이번 운영 QA 조건을 충족할 수 없다.

로컬 설계 초안: private QA 명단에 정확히 2개 slot/중복 없는 auth.uid/만료 시각을 저장하고 postgres 전용으로 관리한다. 제안 기본 60분, DB CHECK 상한 2시간. 회원·anon·service API에는 명단 읽기/등록·수정 권한이 없다. protocol 검사는 QA에게도 먼저 적용한다. entry_open=false일 때 유효한 본인 ID만 기존 테이블 진입 트리거를 통과하고, 일반 회원은 새 protocol이어도 거절된다. 소유권·방장·아이템·결과·XP 권한은 그대로다.

24개 로컬 검사는 원래 게이트의 QA 거부, 자가 등록/제3slot/서비스 API 수정 차단, 구형 QA 탭 거부, A 생성/B 참가/host 시작, 일반 사용자 생성/참가/기존 waiting 시작 거부, guest의 방장 권한 승격 거부, 만료/취소 후 새 입장 거부, 이미 시작된 초기화·heartbeat·기권 허용을 확인했다. 로컬 pgTAP에서 합성 계정과 JWT claim을 모의한 입장 제어 검증이며, 이 초안의 실제 HTTP/Auth 로그인·Edge·React 전체 검증은 아니다. 정식 구현에는 그 검증도 필요하다. 사용자 지정 계정 ID·비밀번호·토큰은 받지 않았고 운영 QA도 생성하지 않았다. 초안은 Git 제외이며 정식 migration·PR #8·20b50fb에 포함되지 않는다.

정식 구현은 기반 게이트 뒤에 의존하는 추가 forward-only migration이 필요하다. 원래 4개를 수정하지 않는다. QA만 추가하면 원래 4+1, 복구까지 별도 파일이면 원래 4+2가 제안될 수 있으나 파일·개수는 승인 전 미확정이다. 새 원문·SHA·회귀를 확정한 뒤 배포 승인을 다시 맞춰야 한다.
