## 측정 범위

2026-11-02 실제 ko.wikipedia.org 문서/revision을 읽었다. source 링크 그래프는 이미 문서에 입장한 상태를 재현해 warm으로 둔다. 새 snapshot은 실제 본문 링크 제목과 fixture 목적지 ID로 준비했고, 기존 로컬 snapshot은 읽기만 했다. 링크 ID 해석의 전체 cold pipeline은 이 아이템 활성화 측정 범위 밖이다. 검색 정제 cache는 snapshot별로 삭제해 Cold5회, 이어 Warm10회를 시도했다. 매번 새 로컬 경기/정상 use RPC로 **15초** 활성화하고 실제 Edge/Auth/RPC를 사용했다. 생성한 계정·방·새 snapshot/cache는 정리했다.

첫 요청은 현재 worker 시작 비용을 포함하지만 매 Cold마다 isolate를 강제 재시작하지 않았다. Cold/Warm은 **정제 문서 cache** 기준이다. Wikipedia 자체의 CDN cache 상태는 통제하지 않았다. nearest-rank p50/p95를 사용하며 n이 작아 p95=최대인 행이 있다. 실패는 실사용 시간0이며 성공 표본에서 제외된 실패 수도 별도 표시한다. 결과를 호스팅된 Production 지연으로 일반화하지 않는다.

## 실패·15초 영향과 개선안

약5.7MB 문서는 parse 성공 시에도 약1.9초 정제 wall time으로 CPU 제한에 가깝고 반복 CPU hard limit로 실패한다. 실패한 활성화는 슬롯을 이미 사용했지만 성공 소비는0이며 deadline을 늘리지 않는다. timeout 상한12초는 유효 시간을 거의 소진할 수 있다. 정상 성공 Cold에서도 최대 약5.05초를 준비에 써서 약9.95초만 남았다. 아래 UI 렌더 측정이 이를 더 줄일 수 있다.

개선 후보는 (1) 중복 AST 재파싱/순회·문자열 조립 비용 감소, (2) 입장 시 같은 snapshot 정제 cache prewarm을 시간창 밖에서 수행, (3) 크기·CPU 예산에 맞는 실패 정책과 안내, (4) cache 읽기에서 HTML/manifest 전체 반복 전송 줄이기다. 어느 안도 이번 후보에서 임의 구현하거나15초를 늘리지 않았다. 서버·화면 정제 일치와 성공 소비/만료 계약을 유지해 재검증해야 한다.

로컬 runner의 user worker 설정은 memory256MB/CPU soft1,000ms/hard2,000ms였으며 CPU hard limit 로그로 원인을 확인했다. 호스팅된 Edge의 CPU2초/메모리256MB 제한도 [공식 문서](https://supabase.com/docs/guides/functions/limits)에 명시돼 있지만 지역·부하·네트워크가 달라 운영 동일 성능을 보장하지 않는다. npm 의존성 사용은 [공식 dependency 문서](https://supabase.com/docs/guides/functions/dependencies)의 지원 범위이며 실제 eszip 번들도 별도 생성했다.
