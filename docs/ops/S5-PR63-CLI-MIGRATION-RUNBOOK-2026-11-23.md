## 승인 후 적용 전 조건

1. 대상 프로젝트·DB endpoint·TLS와 실제 current/session user를 확인한다. 비밀번호는 채팅·URI·명령 인자에
   넣지 않고 검토된 로컬 credential helper로 프로세스 환경에만 제공한다. 종료 후 환경을 지운다.
   CLI **v2.114.0**과 검증한 바이너리/후보 SHA를 고정한다. 임시 role provisioning을 새로 허용하는
   Management API 경로는 이번에 실운영 검증하지 않았으므로 password 경로와 혼용하지 않는다.
2. 원격 PR과 로컬 수정 후보는 아직 다르다. 별도 코드 검토 뒤 사용할 정확한 5개 파일 SHA를 동결한다.
   기존 59개 SHA, 실제 history 59개 버전/행, baseline을 읽기 전용으로 다시 비교한다.
   후보가 다른 환경에 이미 적용돼 있으면 수정본을 재사용하지 말고 그 환경의 이력/내용부터 검토한다.
3. 정상 입장 게이트/운영 점검 수단을 먼저 별도 승인·준비한다. 신규 방/참가/재경기를 멈추고
   진행 경기를 drain한다. 일반전/그룹전 등 공유 RPC 쓰기도 중지해야 한다.
   앱/Worker/관리 작업의 동시 쓰기를 막고 실행자는 1명만 둔다. 데이터 fingerprint의 RR snapshot만으로
   동시 쓰기가 방지된다고 판단하지 않는다. 필요한 게이트나 drain 방법이 준비되지 않으면 BLOCK이다.
4. 운영 최신 전체 백업, 역할/카탈로그/59개 history와 데이터 지문을 로컬 보호 경로에 저장한다.
   신규 Docker에서 실제 전체 복원·원본 대조를 확인한다. 과거 백업만으로 최신 운영 복구를 승인하지 않는다.
5. 만료된 Realtime daily child는 계약과 빈 원본 여부/UTC 보존 기준을 검사해 별도 기록한다.
   다른 schema/owner/ACL/RLS 차이는 자동 수용하지 않는다.
6. CLI pending 목록은 정확히 5개여야 한다. seed/role globals/vault 변환 같은 추가 작업은 섞지 않는다.
   검증 경로는 `db push --db-url ... --skip-vault --yes`였고 DB URL에 비밀번호는 넣지 않았다.
   hosted `--linked` 실제 적용은 이번에 실행하지 않았다. 선택한 연결 경로의 대상/실행 역할을 승인 전에 고정한다.

검토자가 로컬에서 후보 해시를 확인하는 안전한 명령:

```powershell
$manifest = Get-Content server-proposals/pr63-cli-path-20261123/candidate-manifest.json -Raw | ConvertFrom-Json
foreach ($file in $manifest.files) {
  $actual = (Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path 'supabase/migrations' $file.file)).Hash.ToLowerInvariant()
  if ($actual -ne $file.sha256) { throw "후보 해시 불일치: $($file.file)" }
}
```

운영 적용 명령은 자격증명·endpoint·연결 경로·점검 창이 구체화된 별도 승인 패키지에서 확정한다.
이 문서를 보고 지금 실행하지 않는다.

## 중단 시간과 잠금 위험

로컬 실제 CLI 측정: 빈 만료 daily child 3개가 없는 복원본의 **pending 5개 약 13.96초**.
여기에는 로컬 CLI 시작/파싱·SQL 실행이 포함되며, 운영망·동시 세션·I/O·직전 백업 시간은 대표하지 않는다.
이전 초안의 5~10분은 계획 예시다. 운영 창은 입장 중지·drain·Worker 정지·최종 백업/복원·적용·검증·재개를 각각 실측하거나 예산을 배정한 뒤 확정한다.
복원 기반 전체 복구의 RTO/RPO와 트래픽 하에서의 실제 잠금 시간은 **미확인 / BLOCK**이다.

기존 객체 bridge에는 lock_timeout 2초와 statement_timeout 180초가 있다.
신규 설치 분기는 초반 lock_timeout 5초를 적용하고, 후반의 스키마 덤프 초기화가 lock/statement/idle/transaction timeout을 0으로 덮는다.
이는 기존 객체 분기에서 실행되지 않는다. 뒤의 v4 4개에는 별도 파일 내부 timeout이 없고 CLI는 파일 사이에 `RESET ALL`을 한다.
이 timeout은 각각 잠금 대기/개별 문장 제한이며, 전체 파일이나 점검 창의 상한이 아니다.
원본 관계의 ACCESS SHARE 잠금은 정리/DDL과 충돌할 수 있고, ALTER TABLE·제약/인덱스·publication
변경과 함수 교체는 관계/카탈로그 잠금 및 의존성 충돌을 일으킬 수 있다.
읽기/쓰기 트랜잭션이 오래 남으면 대기·실패할 수 있으므로 실제 활성 세션과 장기 트랜잭션을 확인한다.
타임아웃을 임의 확대하거나 정상 사용자 세션을 자동 종료하지 않는다.

RTO는 서비스 차단 또는 장애 감지부터 복구 검증 후 이용 재개까지의 시간이다. 복원·DB/런타임·인증 연결 검증·전환·재개를 포함해 사고 경로별로 측정한다.
RPO는 복구로 돌아갈 시점과 장애 직전 마지막 정상 쓰기 간격이다. 마지막 정상 쓰기 이후 쓰기 차단이 계속되고 그 시점 백업이 복원 검증됐다면 앱 데이터 손실 0이 목표다.
재개 후 추가 쓰기와 플랫폼 관리 데이터는 별도 대조가 필요하다. Supabase 호스팅의 백업/PITR 사용 가능 여부, 복구 대상·보존 기간·전환 시간은 해당 프로젝트에서 확인한다.
Storage 파일, Edge 번들/설정, Worker 실행 상태는 별도 복구 증거로 남긴다. [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups)

## 실패 후 중단·재개

1. 입장/쓰기를 계속 막는다. 같은 CLI를 무작정 반복하지 않고 종료 코드·실패 버전·실제 history를 확인한다.
   네트워크 오류라면 서버 세션 종료 및 커밋 결과를 읽기 전용으로 확인해 결과가 불명확한 상태에서 재실행하지 않는다.
2. S5 파일 또는 그 history INSERT 실패: 로컬에서는 객체·데이터·역할·이력이 전부 59로 원복됐다.
   운영에서도 실제 상태를 대조한다. 권한 계약/드리프트 실패면 권한 확대·fingerprint 갱신으로 우회하지 않는다.
3. 세 번째 파일 실패: 정상 중단점은 **61개**다. 앞 2개는 이미 커밋됐고 실패 파일만 원복된다.
   파일 4/5 실패도 같은 원리다. 5개 묶음 원복을 기대하지 않는다.
4. 일시적 연결/잠금 원인을 해결한 후, 이미 커밋된 파일의 바이트와 이력을 변경하지 않고
   검증된 동일 후보로 정상 CLI를 재개한다. 61→64 및 완료 후 no-op 재실행은 로컬 PASS다.
   후보 SQL 자체 수정이 필요하면 자동 재개하지 말고 새 forward-only 설계/승인을 받는다.
5. 재개 완료 후 전체 보존/권한/이력 검증을 반복한다. 오류가 없다는 이유만으로 곧바로 입장을 열지 않는다.

| 62 | `20261120113647` | v4 검색 계약 정상 |

행 수뿐 아니라 정확한 version prefix와 hash를 대조한다. 표에서 59·61·64는 원자성/재시도 리허설 증거가 있고, 60·62·63은 CLI 파일 커밋 구조에 따른 운영 판단이다.

`migration repair`, 수동 history 등록/삭제, 기존 59개 수정, 강제 schema drop으로 상태를 맞추지 않는다.
신규 설치의 기존 59개에는 과거 wrapper가 남아 있다. 이번 5개 파일 원자성 결과를 과거 전체에
일반화하지 않는다. 신규 빈 DB bootstrap 실패 시 실패 DB를 보존하고 별도 새 DB에서 재검증한다.

## rollback과 실제 복구

- **현재 파일의 커밋 전 실패**: 파일 자체 rollback을 확인한다. 임시 멤버십/CREATE가 남지 않아야 한다.
  이력 INSERT 실패까지 포함한 원자적 rollback은 로컬에서 PASS다.
- **앞선 파일이 이미 커밋됨**: 검증된 기본 대응은 쓰기 정지 상태에서 정상 CLI로 중단점부터 재개하는 것이다.
  기존 manual bridge 역방향 SQL을 이번 5개 전체에 그대로 적용하는 것은 검증한 경로가 아니다.
  `migration down`을 임의 실행하지 않는다. 복원 또는 별도 검토한 forward 보정 중 하나를 승인받는다.
- **전체 복원이 필요함**: 직전 보호 백업을 별도의 신규 환경에 전체 복원하고 owner/ACL/RLS/이력과
  원본 지문을 확인한 뒤, 연결 전환/운영 복구를 별도 승인한다. 원본 DB와 실패 상태를 먼저 보존한다.
  로컬 전체 복원 능력과 운영 자동 복구 RTO가 검증됐다는 것은 다르다.
- **이미 신규 사용자 쓰기가 발생함**: 예전 snapshot을 덮으면 신규 XP/경기 기록이 유실될 수 있다.
  쓰기를 멈추고 최신 추가 백업을 확보해 변경분 보존/대조를 설계한다. 단순 이전 백업 덮어쓰기는 금지한다.
